# shape — 模糊 idea 打磨协议

用结构化追问把一个模糊的想法收敛成精确的 agent-executable spec，输出可直接喂给 /issue 或 /batch-issue。

**触发场景**：用户说"我有个想法"、"我想做X"、"能不能实现Y"、"有个需求但说不清楚"、"/shape [任何描述]"——只要 idea 还不够具体到能直接开 issue，就用这个 skill。不需要用户主动请求，只要发现意图模糊就主动触发。

## 使用方式

```
/shape "模糊想法"   # 带想法直接开始
/shape             # 不带参数，AI 引导输入
```

---

## 执行协议

### 阶段一：追问（覆盖 5 个维度）

**核心原则：一次只问一个问题，对话式推进，绝不一次性抛出问卷。**

目标是覆盖这 5 个维度（顺序按对话自然推进，不强制顺序）：

| 维度 | 追问目标 |
|------|---------|
| **做什么** | 核心功能是什么？解决谁的什么问题？ |
| **不做什么** | 这次明确不碰什么？边界在哪？ |
| **谁用** | 哪个角色/场景触发？用户路径是什么？ |
| **怎么算完成** | 用户做什么操作，看到什么结果算"完了"？ |
| **风险/约束** | 有技术依赖、不能动的东西、或必须满足的条件吗？ |

**追问规则**：
- 从最模糊的维度先问，优先澄清核心
- 用户的回答引出新歧义时，先追这个歧义再继续
- 用户说"差不多了"或连续两轮无新信息 → 进入阶段二
- 最多 7 轮追问，超出自动收敛
- 如果用户给出的想法已经很具体，可以跳过明显已知的维度，直接收敛

---

### 阶段二：收敛（AI 复述，等确认）

5 个维度覆盖后，用一段话复述理解，让用户纠错：

```
好，我理解你想做的是：

[一句话核心目标]

具体：
· 做：[2-3 个核心点]
· 不做：[明确排除的边界]
· 用户路径：[谁，在哪，做什么，看到什么]
· 完成标准：[可验证的条件]
· 约束：[技术/业务限制，无则写"暂无"]

这个理解准确吗？有需要调整的地方吗？
```

等用户确认或修正。修正后重复复述直到用户确认。

---

### 阶段三：输出 spec

用户确认后，根据复杂度自动判断输出形式：

**判断逻辑**：
- 单一功能点、一个 Cursor agent 能独立完成 → **输出 A**（单 issue 格式）
- 多个模块/需要多 agent 并行 → **输出 B**（PRD 格式，喂 /batch-issue）

---

#### 输出 A：单 issue 格式

直接可喂给 `/issue "描述"` 的 body：

```markdown
## 目标

[一句话：让什么从「不存在/不正确」变成「存在/正确」]

---

## AC（验收标准）

- [ ] [从"怎么算完成"提取的可验证功能条件]
- [ ] [可验证的功能条件]

## DoD（完成定义）

- [ ] tsc --noEmit → 0 errors
- [ ] npm run lint → 0 warnings
- [ ] [其他技术条件，无则省略]

---

## 执行步骤

**Step 1：** [基于技术栈推导，含文件路径]
**Step 2：** [...]

## 边界

不做：[out of scope] — 原因：[从"不做什么"维度]
```

输出后问：
```
→ 直接 /issue 开单？还是需要先拆分子任务（/batch-issue）？
```

> 创建时带标签 `shape`，Cursor 凭此过滤高质量任务：
> `/issue "描述" → labels: ["shape"]`

---

#### 输出 B：PRD 格式（master-issue body，喂 /batch-issue）

```markdown
## 目标

[一句话核心目标]

---

## 方案边界

**做：**
- [功能点1]
- [功能点2]

**不做：**
- [排除项] — 原因：[理由]

---

## AC（整体验收标准）

- [ ] [可验证条件1]
- [ ] [可验证条件2]

## DoD

- [ ] tsc --noEmit → 0 errors
- [ ] npm run lint → 0 warnings

---

## 拆解建议

预计 N 个 child-issues：
1. [子任务1：一句话描述]
2. [子任务2：一句话描述]
```

输出后问：
```
→ 先创建 master-issue，然后 /batch-issue #N 自动拆解？
```

> master-issue 和所有 child-issues 统一带标签 `shape`。

---

### 输出末尾必须包含下一步指引

无论输出 A 还是 B，末尾都加：

```
──────────────────────────────
下一步：
  单任务 → /issue "[目标]"        label: shape
  多任务 → 创建 master-issue      label: shape
         → /batch-issue #N       child-issues 统一带 shape

Cursor 批量执行：/cursor --label shape
──────────────────────────────
```

---

## 边界说明

- `/shape` 只负责打磨意图，不创建 issue（创建是 /issue 和 /batch-issue 的事）
- 如果用户在追问过程中不断扩展范围，记录下来但建议拆成独立 /shape 会话处理
- 技术实现细节由 /issue 和 /batch-issue 推导，/shape 只确保功能意图清晰

---

## 自测验收

| 检查项 | 预期结果 |
|--------|---------|
| 追问方式 | 一次一个问题，对话式 |
| 覆盖度 | 5 个维度全部覆盖后才收敛 |
| 收敛检查 | 复述后等用户确认，不自动跳过 |
| 输出格式 | 与 /issue body 格式完全兼容 |
| 复杂度判断 | 正确区分单 issue（输出A）vs PRD（输出B）|
| 下一步指引 | 末尾必须有 /issue 或 /batch-issue 入口 |
| 不越权 | 不自己创建 issue，只产出 spec |
