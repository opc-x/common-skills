# issule-goal — 目标打磨 & 标题锁定

把模糊 idea 或已有 issule 的目标，打磨成极限清晰的一句话，同时生成点题标题。

**两种场景：**
- 新建 issule 前：idea → 目标陈述 → 标题 → 进 /issule
- 已有 issule 更新：重新打磨 #N 的原始目标 → 更新 body + 全局同步 comments

---

## 使用方式

```
/issule-goal <idea>          # 新 idea，打磨目标 + 生成标题
/issule-goal #N              # 读 #N 原始目标，交互打磨（不自动更新）
/issule-goal #N <更新描述>   # 更新 #N 目标 + 全局扫 comments 同步
```

---

## 执行协议

### 阶段 0 — 定位目标锚点

**新 idea 模式：** 从对话输入出发，进阶段 1。

**#N 模式（读已有 issule）：**
1. 读取 issue body，提取**人看区**里的「问题/解决/步骤/结果」四段
2. **这四段是唯一锚点**，后续所有交互都围绕它打磨，不看 comments 里的内容
3. 把原始目标完整展示给用户，确认是这个目标后进阶段 1

```
📌 #N 原始目标：
问题：[从 issue body 读取]
解决：[从 issue body 读取]
结果：[从 issue body 读取]

基于这个打磨，还是有新方向？
```

---

### 阶段 1 — 提炼「让什么变成真的」

必须回答这一个问题：

> 这个 issule 完成后，有一件事从「不存在/不正确/不可用」变成了「存在/正确/可用」。
> 这件事是什么？

用一句话写出来。写不出来 → 返回用户要求澄清。

---

### 阶段 2 — 识别子问题

把总目标拆成 2-4 个独立子问题：

```
□ 可以独立验证（有明确的"做完了"标志）
□ 不与其他子问题重叠
□ 顺序合理（后面的不依赖前面未完成的）
□ 纯业务语言，没有文件名/函数名
```

超过 4 个 → 建议拆多个 issule。

---

### 阶段 3 — 苏格拉底澄清（每次只问一个）

针对边界/验收/依赖/优先级四个维度，有模糊就问，能自己判断的不问：

```
💡 我的推断：[结论]
❓ [一个具体问题]
```

---

### 阶段 4 — 生成标题（必须在输出目标前完成）

目标清晰后，**先锁标题，再写目标陈述**。

标题格式：
```
{emoji} [{优先级}] {类型}: {描述}
```

标题要求：
- 描述部分用业务语言，≤ 20 字，零技术词汇
- 读完 3 秒内知道「这是要解决什么问题」
- 不懂代码的人也能秒懂
- 用具体业务词汇，不用"优化"/"改进"/"处理"等万能词

```
🎯 标题提案：
[emoji] [P?] [type]: [一句话描述]

依据：[一句话说明优先级和类型判断理由]
确认即输出目标陈述；要改直接说。
```

---

### 阶段 5 — 输出目标陈述

```markdown
## 👤 人看区（目标）

**这个 issule 让什么变成真的：**
[一句话，极限精确]

**问题：**
[为什么现在不行，或缺什么，纯业务语言]

**解决：**
① [子问题1]
② [子问题2]
③ [子问题3，可选]

**步骤：**
1. [第一步，业务动词]
2. [第二步]
3. [2-5条]

**结果：**
[触发] → [用户/系统感受到的变化]

**明确不做：**
- [out of scope] — 原因
```

---

### 阶段 6 — 全局同步（仅 #N 更新模式触发）

目标更新后，自动执行：

**Step 6.1 — 读全部 comments**
读取 #N 的所有 comments，找出每条里的「本次更新/当前进度」部分。

**Step 6.2 — 识别过时内容**
对照新目标，标记：
```
□ 哪些 comment 的「当前进度」描述与新目标方向冲突
□ 哪些 comment 的「下一步」已被新目标覆盖或作废
□ 哪些 comment 不受影响（纯技术实现记录）
```

**Step 6.3 — 输出同步摘要，等人确认**

```
🔄 目标已更新，以下内容受影响：

影响的 comment：
  - comment #X（[日期]）：[原描述] → [需要更新为]
  - comment #Y（[日期]）：下一步"XXX"已被新目标取消

不受影响：
  - comment #Z（纯技术执行记录，不需要动）

回复「ok」更新受影响的 comments；要跳过某条说「跳过 #X」。
```

**Step 6.4 — 执行更新**
用 `mcp__github__update_issue` 更新 issue body（人看区部分），
用 `mcp__github__add_issue_comment` 追加一条「目标更新记录」：

```markdown
## 🔄 目标更新记录

**原目标：** [一句话]
**新目标：** [一句话]
**变更原因：** [用户说的 or 推断的原因]
**受影响的步骤：** [列出哪些步骤要重新执行]
```

---

### 阶段 7 — 自检

```
□ "让什么变成真的"一句话写得出来？
□ 子问题之间没有重叠？
□ 步骤用业务动词，没有文件名/函数名？
□ 结果格式是「触发 → 变化」？
□ out of scope 明确列出？
□ 标题 3 秒内能理解是干什么的？
□ 读完 30 秒内能理解全貌？
```

## 典型对比

```
❌ 模糊
"优化一下课程相关的东西"

✅ 打磨后
让什么变成真的：每节课有一张与词汇内容匹配的场景图，用户打开课程立刻看到
标题：🟢 [P2] feat: 191课场景图 pipeline — prompt 就绪，生图解锁
问题：191课场景图全空，看图说话卖点对用户不可见
解决：① schema 扩列 ② 数据质检 ③ 生成 prompt ④ 代码同步
结果：打开任意一节课 → 看到场景插画 → 开口不尴尬
不做：生成图片本身（那是 #17 的事）
```

```
❌ 模糊
"修一下 SRS 的问题"

✅ 打磨后
让什么变成真的：用户学完一节课后，复习队列里出现这节课的题目
标题：🔴 [P0] fix: 完成课程不写复习队列 → SRS 永远空
问题：completeLesson() 不写 review_schedule，复习页永远空
解决：① 课程完成时批量写入 ② 去重防止重复写入
结果：完成 Lesson 1 → 明天打开复习页 → 看到题目
不做：SRS 算法本身（已有，不改）
```

## 行为准则

| 应该做 | 不应该做 |
|--------|---------|
| #N 模式始终从 issue body 人看区读原始目标 | 从 comments 里读目标（comments 是过程记录）|
| 先锁标题，再输出目标陈述 | 跳过标题直接写目标 |
| 标题用业务词，3秒能识别 | 标题用"优化"/"处理"/"改进"等万能词 |
| 更新目标时，扫全部 comments 识别过时内容 | 只更新 body，不管 comments 的一致性 |
| 每次只问一个问题 | 列出一堆问题让用户填表 |
| 确认标题后才输出目标陈述 | 标题和目标同时扔出来 |
