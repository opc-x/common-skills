# issule — Idea → Agent-Ready Issue

从一个粗糙 idea 出发，模型主动读代码库、填技术上下文、逐步打磨，
直到生成一个 AI Agent 拿到就能执行的 Issue。

**人只负责提 idea + 回答模型真的搞不定的问题。其他全是模型的事。**

---

## 使用方式

```
/issule <idea>               # 一句话 idea，模型接管后续，默认 talkflow
/issule <idea> <repo>        # 指定仓库
/issule <idea> dry           # 只生成草稿，不创建 GitHub Issue
/issule comment <#N> <描述>  # 给 Issue #N 追加一条结构化迭代评论
```

**默认 Milestone = 当天日期（YYYY-MM-DD）**
不特别说明，所有 issue 自动挂到今天的 milestone。milestone 不存在则自动创建。
等于每天有一个"今日待办"分组，按天追踪进度。

**Milestone 口语约定（模型必须识别）：**

| 用户说 | 实际含义 |
|--------|----------|
| issule / 今天的 issule | 今天日期的 milestone 下所有 issue |
| 昨天的 issule | 昨天日期的 milestone 下所有 issue |
| 明天的 issule | 明天日期的 milestone（提前创建/规划） |
| 本周的 issule | 本周一到今天，所有日期 milestone 的 issue 合集 |

模型收到上述词时，自动换算成对应日期范围，不需要用户解释。

---

## 标题格式（强制，所有 Issue 必须遵守）

```
{emoji} [{优先级}] {类型}: {一句话描述}
```

| 字段 | 选项 | 规则 |
|------|------|------|
| emoji | 🔴🟡🟢🔵🟣 | 见优先级对照表 |
| 优先级 | P0/P1/P2/P3 | P0=主流程阻断；P1=核心功能缺失/严重bug；P2=体验提升；P3=维护/重构 |
| 类型 | fix/feat/chore/spike | 对应 conventional commit |
| 描述 | 业务语言，≤20字，零技术词汇 | 不懂代码的人也能秒懂 |

**优先级 emoji 对照：**
- 🔴 P0 — 主流程阻断，必须先修
- 🟡 P1 — 核心功能缺失或严重 bug
- 🟢 P2 — 体验提升、非阻断性功能
- 🔵 P3 — chore / 重构 / 维护
- 🟣 spike — 探索/调研，无确定产出

**示例：**
- `🔴 [P0] fix: 课程完成不写复习队列 → SRS 永远空`
- `🟡 [P1] feat: 看图说话 — 课程界面展示配套场景图`
- `🟢 [P2] feat: Hero Demo 气泡改为逐条延迟出现`
- `🔵 [P3] chore: onboarding 全流程 E2E 冒烟验证`

## 执行协议（模型必须严格遵守）

### 阶段 0 — 理解 Idea

从对话上下文 + 用户输入提取方向和仓库。

**处理不同成熟度的 idea：**
- idea 清晰（有明确目标）→ 直接进阶段 1
- idea 模糊（"优化一下 XX"）→ 模型先推断最可能的具体目标，用阶段 2 的格式确认一次，再进阶段 1
- idea 极度模糊（"让产品更好"）→ 必须先用阶段 2 提炼出具体方向，不得跳过

**不问废话，只在无法推断时才问。**

---

### 阶段 1 — 模型自主调研

两条腿并行，**不依赖用户**：

**1.1 读本地代码库**
- 找相关文件（`find` + `grep`）
- 读关键文件，确认现状、缺失点、可复用代码
- 从 `package.json` / `tsconfig.json` 读技术约束

**1.2 联网查最新信息（强制，以下情况必须触发）**

```
触发条件（满足任一即必须 WebSearch，不得跳过）：
□ 涉及第三方库（Stripe / Supabase / Next.js / Framer Motion 等）
□ 需要确认某个 API 的当前签名或推荐写法
□ 方案可能有 breaking change 或已知 bug
□ 不确定某个功能的当前最佳实践

搜索格式：[库名] [功能关键词] 2025 OR site:官方文档
```

**1.3 影响范围**
- 改动影响哪些文件？有没有依赖链？有没有 schema 变更风险？

---

### 阶段 1.5 — 锁标题（先于正文，人确认才往下走）

调研完成后，**写正文之前**，先提案标题：

```
🎯 标题提案：
[emoji] [P?] [type]: [一句话描述]

依据：[一句话说明优先级和类型的判断理由]
确认即写正文；要改直接说。
```

**人确认或修改 → 标题锁定。锁定后不得修改。**

锁定后，正文所有内容必须服务于这个标题：
- 标题说 `fix` → 正文只写修复，不扯功能迭代
- 标题点名的模块 → 正文不涉及其他模块
- 任何与标题无关的内容 → 归入「边界 > 不要碰」，不写进正文主体

---

### 阶段 2 — 苏格拉底式补全（只问人搞不定的）

**每次只问一个问题，给出推断让用户确认或纠正。**

```
💡 我的推断：[基于代码+搜索得出的结论]
❓ 有一件事我无法从代码里确认：[具体问题]
```

能自己推断的，直接跳阶段 3。

---

### 阶段 3 — 逻辑闭环检查

模型自己走一遍执行路径，逐条确认：
```
Step N → 需要前置条件 X → X 存在？[是/否]
Step N → 写入/调用 Y → Y 的签名/schema 正确？[是/否]
最终结果 → 验收条件可自动验证？[是/否]
```
发现漏洞：能自己修就修，必须人决策才回阶段 2。

---

### 阶段 4 — 生成 Issue 草稿

**标题北极星原则（写完草稿必须自检）：**
逐节扫一遍：「这节内容，和锁定的标题直接相关吗？」
- 相关 → 保留
- 无关但重要 → 移入「边界 > 不要碰」并注明
- 无关且不重要 → 删除

**双层结构。顶部给人（纯业务，5秒看懂），底部给 Agent（技术细节，防跑偏）。**

```markdown
## 👤 人看区
> 极低认知负担，纯业务语言，无技术词汇

**问题：** [一句话，说清楚什么坏了或缺什么]

**解决：**
① [子问题1，一句话]
② [子问题2，一句话]
③ [子问题3，可选]

**步骤：**
1. [第一步做了什么，业务动词]
2. [第二步做了什么]
3. [第三步，2-5条]

---

## 多维验收评分（Agent 自循环目标）

> Agent 执行完后对每维度自评，**未达标继续迭代，全达标才 PR ready**。

| 维度 | 目标 | 评分标准（如何打高分）| 低分时怎么改 |
|------|------|---------------------|-------------|
| **功能完整性** | ≥90 | 所有验收 checkbox 通过，无遗漏场景 | 逐条跑验收标准，找到未覆盖的 case 补上 |
| **代码健壮性** | ≥85 | 错误路径有处理，不静默吞异常，边界值不崩 | 检查每个 await 有没有 try/catch 或错误判断 |
| **类型安全** | ≥95 | `tsc --noEmit` 零错误，无 `any` 滥用 | 跑 tsc，逐个修类型错误 |
| **副作用控制** | ≥90 | 只改 in scope 文件，不引入新依赖，不破坏现有测试 | git diff 检查改动范围是否超出预期 |
| **可维护性** | ≥80 | 逻辑清晰，变量命名自解释，无魔法数字 | 给魔法数字加常量，给复杂逻辑加单行注释说明 why |

**Agent 自评输出格式（每轮迭代后必须输出，不得省略）：**
```
=== 迭代 N 自评 ===
功能完整性：XX/100 — [一句话理由]
代码健壮性：XX/100 — [一句话理由]
类型安全：  XX/100 — [一句话理由]
副作用控制：XX/100 — [一句话理由]
可维护性：  XX/100 — [一句话理由]

未达标：[维度名 XX分 → 具体改哪里]
下一步：[改完后再跑一遍自评]
全达标：PR ready ✅
```

## 验收标准

> 写法规则：每条必须是"操作 → 预期结果"格式，Agent 可自动验证，不依赖人眼判断。
>
> ✅ 好的写法：完成 Lesson 24 后查 `review_schedule` 表，`user_id=当前用户` 的行数 > 0
> ❌ 坏的写法：复习功能看起来正常

- [ ] [操作] → [可验证的预期结果]
- [ ] `tsc --noEmit` 输出零错误
- [ ] [边界场景] → [预期结果]
- [ ] 重复触发同一操作 → 数据不重复/不报错

## Agent 执行协议

### 执行前
1. 通读 Issue，对照「技术上下文」确认每个文件路径实际存在
2. 列出执行计划：`Step 1 → Step 2 → ... → 自评`
3. 有歧义先按技术约束推断；推断不了才中断

### 执行中
- 每完成一步立刻对照验收标准自检
- Out of scope 的记录但不执行
- 不引入 Issue 未提及的新依赖

### 执行后（自循环验收 + 强制追加报告）
1. 输出多维自评（见上方格式）
2. 有未达标维度 → 按"低分时怎么改"执行，重新自评
3. 全部达标 → **必须将执行报告 POST 到本 Issue 的 comment**（见下方格式），再通知人做最终验收

**执行报告格式（全部达标后强制输出到 Issue comment）：**

```markdown
## 👤 执行报告

**状态：** ✅ 全部达标 / ⚠️ 部分达标 / ❌ 未达标

**做了什么：**
1. [第一步完成情况]
2. [第二步完成情况]

**验收结果：**
- [x] [验收项] → [实际结果]
- [x] tsc --noEmit → 零错误

**需要人工确认：**
- [需要人看的项，没有则写"无"]

---
🤖 以下为 Agent 技术细节

**多维评分（最终）：**
功能完整性：XX/100
代码健壮性：XX/100
类型安全：  XX/100
副作用控制：XX/100
可维护性：  XX/100
```

**POST 方式（用 GitHub API，需要 GITHUB_TOKEN 环境变量）：**
```ts
await fetch(`https://api.github.com/repos/HcPittBrad/talkflow/issues/${ISSUE_NUMBER}/comments`, {
  method: "POST",
  headers: { Authorization: `Bearer ${process.env.GITHUB_TOKEN}`, "Content-Type": "application/json" },
  body: JSON.stringify({ body: report }),
});
```

### 只有以下情况才中断找人
- 验收标准之间存在矛盾
- 完成任务必须修改 out of scope 内容
- 涉及 DB schema 变更
- Issue 中技术信息有误（文件不存在 / 接口签名不匹配）
```

### 阶段 6 — 创建 Issue

用户确认后，按顺序执行：

**Step 6.1 — 解析 milestone ID（用 gh CLI）**

```bash
# 今天日期
TODAY=$(date +%Y-%m-%d)
REPO="HcPittBrad/talkflow"

# 查今天的 milestone 是否已存在
MILESTONE_NUM=$(gh api repos/$REPO/milestones \
  --jq ".[] | select(.title==\"$TODAY\") | .number")

# 不存在则创建
if [ -z "$MILESTONE_NUM" ]; then
  MILESTONE_NUM=$(gh api repos/$REPO/milestones \
    -X POST -f title="$TODAY" \
    --jq ".number")
fi

echo "Milestone #$MILESTONE_NUM: $TODAY"
```

**Step 6.2 — 创建 Issue**

调用 `mcp__github__create_issue`：
- `owner`: `HcPittBrad`，`repo`: 默认 `talkflow`
- `title`: 阶段 1.5 人确认的锁定标题，原文照搬，**不得修改**
- `milestone`: Step 6.1 拿到的数字 ID
- `labels`: 根据类型自动选（`enhancement` / `bug` / `design`）

**Step 6.3 — 输出给 Agent 的提交格式**

Issue 创建成功后，**必须**输出以下格式供用户复制给任何 Agent（Cursor/Claude Code 等）：

```
✅ Issue #N 创建成功

给 Agent 的提交格式（第一行=会话标题，直接复制）：
──────────────────────────────────────────
#N <issue 标题>
https://github.com/HcPittBrad/<repo>/issues/N
──────────────────────────────────────────
```

说明：第一行作为 Agent 会话标题，第二行 Agent 读取完整任务上下文。

## 模型行为准则

| 模型应该做 | 模型不应该做 |
|-----------|-------------|
| 主动读代码找答案 | 把能自己查的问题抛给用户 |
| 每次只问一个问题 | 列出一堆问题让用户填表 |
| 给出推断让用户确认 | 空手问"请描述技术约束" |
| 联网查最新信息（满足触发条件必查）| 只靠训练数据下结论 |
| 实现方案附具体代码片段 | 写伪代码或"根据实际情况实现" |
| 验收标准写"操作→预期结果"格式 | 写"功能看起来正常"这类主观条件 |
| 评论包含分数 delta 对比 | 评论不记录与上一轮的变化 |
| 低分维度按指引方向迭代 | 无方向地重写代码 |
| 阶段 1.5 先锁标题，等人确认再写正文 | 调研完直接写正文，标题最后才起 |
| 正文每节自检是否锚定标题 | 把无关内容塞进正文主体 |
