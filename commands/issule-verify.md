# issule-verify — 执行后量化验收

**issule 是人机协同的契约。** 这个 skill 以 issule 为唯一锚点，
从中推导出所有验收逻辑，不依赖任何硬编码类型。
适用于任何 issule，不管是 schema/代码/数据/内容/UI。

三层验收：
- **Tier 1** 数字化：直接跑，出数字，不过脑
- **Tier 2** AI推理：当前订阅推理，不调额外接口
- **Tier 3** 人工：给步骤不给判断题，30秒内完成

---

## 使用方式

```
/verify-issule #N        # 验收指定 issue（默认 talkflow repo）
/verify-issule #N <repo> # 指定仓库
```

---

## 执行协议

### Step 1 — 读取 issule 全文（锚点建立）

读取 issue body + 所有 comments（含 Cursor 执行报告）。

从中提取三类信息：

```
① 承诺的目标
   "让什么变成真的"——人看区的问题/解决/结果

② 已有的验收条件
   body 和 comments 里所有 - [ ] checkbox

③ 改动的事实
   做了什么：新增了什么/修改了什么/删除了什么
   Agent 区的 Step 列表、migration SQL、代码片段
```

---

### Step 2 — 从 issule 推导量化指标

**不用硬编码类型，读懂 issule 做了什么，自己推导最有价值的量化检查。**

推导逻辑：

```
读到"INSERT INTO / upsert"
  → 推导：目标表行数是否等于预期？有无 null 在非空列？

读到"ALTER TABLE ADD COLUMN"
  → 推导：information_schema 里字段是否存在？有 CHECK 约束的字段是否有边界值？

读到"UPDATE ... SET"
  → 推导：被更新的列，是否所有行都被覆盖到了？有无遗漏？

读到"tsc / TypeScript"
  → 推导：tsc --noEmit 是否零错误？

读到"新增 prop / 组件改动"
  → 推导：grep 目标 prop 是否出现在改动文件里？

读到"API 过滤条件"
  → 推导：直接查 DB，验证过滤逻辑是否生效？

读到"幂等性"关键词
  → 推导：重复执行关键操作前后，核心数据行数是否不变？

读到"AI 生成内容"
  → 推导：抽样内容，AI 推理质量是否达标？给出抽查样本和判断标准。

读到"用户界面变化"
  → 推导：无法自动验证，生成人工步骤（打开哪个 URL，看什么，判断什么）。
```

推导出来的指标优先级排序标准：
```
最高价值 = 直接反映「让什么变成真的」这个核心承诺
次高价值 = 反映数据完整性和正确性
最低价值 = 反映过程执行（不是结果）
```

---

### Step 2.5 — 人工确认量化指标（执行前快速过一遍）

推导完指标后，**在执行之前**，把准备跑的指标列给人看：

```
📋 准备验收 #N，将执行以下检查：

Tier 1（自动跑）：
  1. SELECT count(*) FROM scenes WHERE image_prompt IS NOT NULL → 期望 191
  2. tsc --noEmit → 期望 0 错误
  3. grep "sceneTitle" components/learn/session-card.tsx → 期望有输出

Tier 2（AI 推理）：
  4. 抽查 10 条 scenes.title，判断是否有画面感

Tier 3（需要你操作）：
  5. 打开 /learn/1/1，确认标题是动态的

这些指标是否覆盖了你最关心的验收点？
回复「ok」直接跑；要调整直接说。
```

**人的决策成本 = 5秒扫一眼**，不是让人重新设计指标。

---

### Step 3 — 三层验收执行

#### Tier 1：数字化验收

- 构造 SQL / Bash / grep 命令
- 用 Supabase MCP 或 Bash tool 直接执行
- 对比期望值

```
输出格式：
✅ [验收项] → 实际值=[X]，期望=[Y]
❌ [验收项] → 实际值=[X]，期望=[Y] → 修复建议：[一句话]
```

#### Tier 2：AI推理验收

- 从 DB 或文件取 5-10 个样本
- 应用 issule 里的具体判断标准
- 给出：判定结果 + 置信度 + 抽查样本 + 理由

```
输出格式：
⚠️ [验收项]（置信度 XX%）
   抽查样本：[样本1] / [样本2] / ...
   判定：[通过/不通过] — [一句话理由]
```

置信度 < 60% 时自动降级到 Tier 3。

#### Tier 3：人工验收

**给步骤，不给判断题。人只需要执行，不需要思考。**

```
输出格式：
👤 [验收项]（预计 N 秒）

→ 第1步：[具体操作，精确到点击哪里/打开哪个URL]
→ 第2步：[看什么/找什么]
→ 第3步：符合预期 → 回复"✅"；不符合 → [截图/描述X]发给我

AI 无法自动判断的原因：[一句话]
```

---

### Step 4 — 生成验收报告并 POST 到 Issue

**必须以 YES 或 NO 开头。** 这是人 3 秒能看懂的结论，其余是依据。

判定规则：
```
YES → Tier 1 全部通过 + Tier 2 置信度均值 ≥ 80% + 无 Tier 3 待办
 NO → 任何 Tier 1 失败 / Tier 2 均值 < 80% / 有未处理的 Tier 3
```

报告格式：

```markdown
## 验收报告：#N <issue 标题>

# ✅ YES — 可交付
（或）
# ❌ NO — X 项未通过，不可交付

> 执行时间：<timestamp>

---

### Tier 1 数字化结果（X/Y 通过）
✅ [验收项] → 实际=X，期望=Y
❌ [验收项] → 实际=X，期望=Y → 修复：[一句话]

### Tier 2 AI推理结果
⚠️ [验收项]（置信度 XX%）
   样本：[样本1] / [样本2]
   判定：[通过/不通过] — [理由]

### Tier 3 待人工确认
👤 [验收项]
→ 第1步：[操作]
→ 第2步：[看什么]
→ 第3步：符合 → 回复"✅"；不符合 → 发截图

---

### ❌ 未通过项修复清单（NO 时必须列出）

| 项目 | 实际 | 期望 | 修复命令/方向 |
|------|------|------|--------------|
| [项目名] | [X] | [Y] | `[具体命令或操作]` |
```

POST 方式：
```ts
await fetch(`https://api.github.com/repos/HcPittBrad/talkflow/issues/${N}/comments`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.GITHUB_TOKEN}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ body: report }),
});
```

## 行为准则

| 应该做 | 不应该做 |
|--------|---------|
| 从 issule 内容推导指标，不硬编码类型 | 按照"这是 schema 类 issule 所以检查这些" |
| 核心指标直接反映「让什么变成真的」 | 检查无关紧要的过程指标 |
| Step 2.5 先给人过一眼指标再跑 | 不打招呼直接执行 |
| 人工验收能砍就砍，0 是最优解 | 惯性地把所有主观项都扔给人 |
| Tier 3 给步骤，让人秒执行 | 让人"判断是否正确"、"感受体验" |
| AI置信度 < 60% 自动降级到 Tier 3 | 低置信度强行输出 AI 判定 |
| 有 ❌ 立刻给修复方向 | 只报告问题 |
| 全部通过才说可交付 | Tier 3 未完成就说通过 |
